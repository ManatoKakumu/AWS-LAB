# 05-ecs-autoscaling

## 課題内容(メンターから提示された要件)

`01-vpc-network`ではECS Service/ALBを構築しましたが、タスク数は固定(desired count固定)のままでした。今回はこのサービスにECS Service Auto Scalingを導入し、負荷に応じてタスク数が増減する構成にします。

Application Auto Scalingには大きく2種類のポリシーがあります。

- **Target Tracking Scaling Policy**(目標値追従型)
- **Step Scaling Policy**(段階型)

やってもらいたいこと:

1. 上記2種類のポリシーの違いを調べ、今回のユースケース(ECS Fargateサービスの負荷対応)にどちらが適切か、理由とともに自分で判断する
2. 判断したポリシーについて、以下を設計として言語化する
   - どのメトリクスでスケーリングを判断するか(CPU使用率 / ALBRequestCountPerTarget 等)とその選定理由
   - 目標値・しきい値をどう設定するか、その根拠
3. ALBのヘルスチェック設定(healthy threshold / unhealthy threshold / interval / timeout)が、スケールアウト時(新規タスクがトラフィックを受け始めるタイミング)とスケールイン時(タスクが安全に登録解除されるまでの猶予)にどう作用するかも設計に含める
4. 設計がまとまったらAWSコンソールで構築し、実際に負荷をかけてスケールアウトする様子、負荷を止めてスケールインする様子を、CloudWatchメトリクスやECSサービスのイベント履歴から観察する
5. 観察が終わったらTerraformでコード化する

## 前提・制約

- `01-vpc-network`で構築したVPC・ALB・ECSクラスター・ECS Serviceを流用してよい(ネットワーク設計・ALB自体の再設計は不要。ただしECS Serviceはdesired count固定からAuto Scaling対応の構成に変更が必要)
- 負荷生成は、外部の負荷試験ツールを使う必要はない。コンテナ内で`stress`コマンドを使う、意図的に重い処理を返すエンドポイントを叩く、など簡便な方法で代用してよい
- コスト: Fargateタスクが複数起動する時間帯が発生する。確認が終わったら速やかにdesired countを最小値に戻す、またはdestroyすること。長時間の高スケール状態を放置しない

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
| NAT Gateway経由のアウトバウンド通信(イメージ取得等)の出口、およびALBが外部からのリクエストを受けるための入口の両方に用いる | IGW | 代替サービスがない |
| 外部からのリクエストをECSタスクへ振り分ける | ALB | Webサイトを想定しているため、NLBではなくALBを選定 |
| プライベートサブネットに配置したECSが、イメージ取得等でインターネットと通信する際に経由する | NAT Gateway | 異なるAZ間の通信には課金が発生するが、ECS Serviceの起動先サブネットを1つのAZに限定することで、AZをまたぐ通信自体が発生しない構成にできる。そのためNAT Gatewayを複数配置してAZごとに用意する必要がなく、コストの高い複数配置は行わず1台のみとした |
| コンテナを起動し、実際のアプリケーション処理(Webアプリの提供)を行う | ECS | EC2インスタンスなどでも目的は達成できるが指定されたのでECSとした（長期運用するか、インフラ管理の容易性、Webサイトや軽量処理などの用途によって適切な選択は変わる） |
| CPU使用率に応じてECSのタスク数を自動的に増減させる | Application Auto Scaling | 代替サービスがない |
| Application Auto Scalingの設定に伴いアラームが自動作成され、メトリクスのしきい値超過を検知する | CloudWatch | 代替サービスがない |

### スケーリングポリシー設計
- ターゲット追跡ポリシー
  - CPU使用率やリクエスト数などにおいて、数値を決め、その数値に近くなるようにスケールする
  - 例えば、CPU使用率70%の時が最も高いパフォーマンスを発揮するのであれば、CPU使用率を70%と指定した際に、CPU使用率が70%を下回れば70%に近づくようにスケールインし、逆であればスケールアウトして1台当たりの負荷を下げることで70%に近づけようとする
  - AWS側でどれくらいスケールするかを算出される
- ステップスケーリングポリシー
  - CPU使用率を60%が標準としたときに、10%超過していたら1台追加で起動、20%超過していたら3台追加で起動、というように自分で柔軟にスケール設定を行うことが可能
  - ただし事前に過去のデータなどを収集し、それに基づいて適切に決定、運用後も設定が適切かを継続的にモニタリング・改善する必要があり、柔軟な設定がしたい際には良いが、運用コストが高くなる可能性がある
- 今回使用するスケーリングポリシー
  - ターゲット追跡ポリシーを採用
    - 過去データがない、継続的に運用改善する対象ではない、より柔軟にスケール設定を行うメリットがない（目的はスケールアウト・インの挙動を確認することにある）、などが理由となる
  - CPU使用率70%を閾値とする
    - ALB1台当たりのリクエスト数、通信量などもあるが、それよりもユーザへのレイテンシを最小限にすることが第一だと考えており、そのためにはリクエスト数の多さではなく、コンピューティング資源の負荷量を見るべき
    - 仮に閾値を90%などにすると継続的にリクエスト数が増えた際に、閾値が高すぎてスケールアウトの命令発生が遅れ、リソースの起動時間もあるので、その後のリクエストをさばききれなくなる可能性があるので、ある程度の余裕を持たせたい。一方で、低すぎると、コストが高くなるのでこれらを踏まえ、70%とした
    - 今回は1回きりだが、実務などでは、継続的にメトリクスの監視やデータ収集をして、モニタリング・改善していくべきもので、最初に決めたら終了という類の話ではない
  - ALBRequestCountPerTargetを使い、CPU使用率の監視だけでは気づけない、DBからのレスポンス待ちの状況を把握することも視野に入れるべきだが、今回はDBは出てこないので無視する
- ターゲットグループの min/max capacityについて
  - max:2
    - これは予算や予想（もしくは過去データあればそれも使う）最大リクエスト数に耐えられるような数値にて設定すれば良い
    - 今回はスケーリングの挙動確認が目的なので、2としている（実際はもっと大きな数値を設定することになるはず）
  - min:1
    - これはmaxと同じく、予想最小リクエストに耐えられるような数値で行えばよいが、可用性を考慮するのであれば、最低2AZでは稼働させるべきなので、2以上は必要になる
    - 今回はスケーリングの挙動確認が目的なので、1としている

### ヘルスチェック設計
- インターバル
  - 10秒
  - 短すぎるとリソースダウンの検知が早くなるが、通信量が増え、負荷が大きくなる
  - 長すぎると検知までに時間を要し、ダウンしているリソースにリクエストが飛ばされる懸念がある
  - ただ今回はスケールアウトの挙動を確認することが目的で、ぞれを早く確認したいので、少し小さめの数値を設定する
  - 以上を踏まえ、間をとる感覚で10秒とする
- タイムアウト
  - 5秒
  - 長すぎるとヘルスチェック失敗の判定に時間がかかるのでリソースダウンの検知の遅れ、およびダウンしたサーバへのトラフィックが増える可能性あり
  - そもそもユーザ体験を考慮すると、正常に動作していてもレスポンスが遅すぎるのはよくないので、過度に長くする必要はない（ただし、これはアプリコードやクエリの書き方、適切なインデックス欠如などの問題があり、ヘルスチェックとは別の観点の話が絡むかもしれないが）
  - 短すぎると正常に動作していても失敗と見なされる可能性がある
  - 以上をふまえ、5秒とする
- 正常閾値
  - 2回
  - 多すぎると、スケールアウトする際に中々新規で起動したリソースへトラフィックが送信されない
  - 少なすぎると、成功や失敗を繰り返す不安定な状態でも正常であるとみなされる可能性がある
  - ただ今回はスケールアウトの挙動を確認することが目的で、ぞれを早く確認したいので、少し小さめの数値を設定する
  - 以上より、2回とする
- 異常閾値
  - 3回
  - 少なすぎると、正常に動作していてもリクエスト急増時に異常であると判断され、トラフィックが送信されなくなる+新規のリソース稼働までに時間がかかるため、その間の残りのリソースへの負荷が高くなり、レイテンシが高くなってしまう
  - 多すぎると、異常なリソースへのリクエスト送信が増える可能性がある
  - 以上より、3回とする
- 登録解除の遅延
  - 30秒
  - ターゲット先がリクエスト処理にかかる時間より少し多め(1.5～2倍程度)を設けるとよいと判断した
  - かりに短くすると、正常なリクエストであっても、レスポンスが到達せず、再度同様のリクエストを投げることとなり、ユーザ体験が悪化する
  - ただ今回はスケールの挙動確認が目的なので、そこまで気にしない
  - 以上より、30秒とする

  - Inbound：0.0.0.0/0 TCP 80

### 可用性設計
- ALBは複数AZに配置しているので、単一AZ障害による可用性低下を避けることが結果としてできているが、今回は可用性はそこまで重視しておらず、ALBは複数AZに配置する必要があるという制約に大きく引っ張られたという形になった
- NAT Gatewayは単一AZに配置しているが、今回のスケーリング挙動を確認するのが目的、というケースにおいては可用性を高く維持するよりもNAT Gateway起動時間当たりのコストを下げることを優先した
- ECSも単独AZ配置としており、何らかのサービスを提供するなどであればマルチAZ構成にしたほうが良いが、今回の目的からもその必要はないと判断し、シングルAZ構成にした

## わからなかったこと・迷ったこと
- ALBRequestCountPerTargetについて
  - コンテナがDBへの通信を行う際に、DBの負荷が高く、処理待ちしている場合はCPU使用率が上昇しないため、CPU使用率だけを見ても異常に気付きにくい
  - そのため、ALBへのリクエスト数を見ることでリクエストのたまり具合、というCPU使用率だけでは見えない観点から監視することが可能
- ヘルスチェックの数値設定
  - 実際に許容できる時間で新規リソースへのトラフィック分散開始ができるように、設定する
  - まずはデフォルトからはじめて、問題があれば改善するパターンが取られることが多い
- 登録解除の遅延
  - 正常なターゲットが意図的に外される（スケールインなど）時に発動するもの
