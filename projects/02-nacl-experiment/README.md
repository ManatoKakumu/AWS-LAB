# 02-nacl-experiment

## 課題内容(メンターから提示された要件)

NACL(ネットワークACL)のステートレス挙動を、実機で意図的に壊してから直す形で体験する。**この段階ではコードや構築の話は持ち込まない。まず「何を、どういう手順で確認するか」の実験設計をまとめ、レビューを受けること。**

### 満たすべき要件

- 検証用の最小構成を自分で設計する(3層アーキテクチャは不要。NACLの挙動確認に必要十分な規模でよい)
- 対象サブネットのNACLを、デフォルト(全許可)から**明示的なInbound/Outboundルールを持つカスタムNACL**に置き換える
- 以下の2パターンを**この順番で**実機検証できるように設計すること
  1. **意図的に壊す**: インバウンドは許可するが、戻りの通信に必要なエフェメラルポートのOutboundルールを欠落させた状態を作る
  2. **直す**: エフェメラルポートのOutboundルールを追加し、通信が復旧することを確認する
- 上記と同じ通信パターンに対して、セキュリティグループ(ステートフル)ではどう挙動が異なるかを対比できるように設計する(NACLだけ壊れてSGは影響を受けない、という対比が実機で見えることが望ましい)
- **構築前に予測を書くこと**: 各ステップで「通信は成功するか失敗するか、失敗するなら何が原因か」をREADMEに事前に記述し、レビューではその予測の妥当性を問う

### 特に意識してほしい観点

- なぜNACLでは戻りの通信のトラフィックにも明示的なルールが必要なのか(SGとの違いの根本原因)
- エフェメラルポートとは何か、範囲はどう決まるか、どちら向き(クライアント側/サーバー側)のどのポートに影響するか

## 前提・制約

- 目的は実験であり、本番相当のアーキテクチャは不要。NAT Gateway/ALB/ECS/RDSなど時間課金・高コストなリソースは使わない設計にすること(EC2インスタンスは無料利用枠のインスタンスタイプを想定)
- 通信確認の方法(SSH/curl/pingのどれを使うか、踏み台はどう用意するかなど)は自分で設計してよい。VPC Reachability Analyzerのようなツールを使う設計でもよいが、その場合も「実際のトラフィックで確認する」要件を満たせるか検討すること
- 予算: 学習用AWS費用は月数千円程度まで許容。ただし本課題はごく小規模構成を想定しており、追加コストはほぼ発生しない設計を求める
- リージョン: ap-northeast-1(既定。変更する場合はここに明記)
- 進め方: 設計 → メンターによる設計レビュー → (合格後)AWSコンソールで構築・実機検証 → 同じ構成をTerraformでコード化、の順で進める
- Terraform実装時の追加要件: NACLのルールエントリなど同一パターンが繰り返される箇所は、`01-vpc-network`のような手打ちの列挙ではなく、`variable`と`for_each`を使って抽象化すること

## 設計

### 構成図
- `02-nacl-experiment.drawio` に記載

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
|実機からEC2へ通信テストをする際に必要|IGW|外部発信の通信のため、NAT Gatewayは不可|
|NACLやSGの動作確認をする際に使うためのリクエスト先リソース|EC2|特になし。簡単に起動ができるため。OSなどの管理が必要だが、それはあくまで長期利用の話であり、今回のような実験であれば運用コストはほぼ見積もらなくてよい（期限の長い実験なら別かもしれないが）|

### ルートテーブル設計
- Public subnet
  - local：デフォルトで設定のため明示的に記載は不要。ただし今回はこれが使われることはない
  - 0.0.0.0/0 IGW：サブネットリソースにパブリックIPアドレスが付与されれば外部からアクセスを許可したいのでNAT Gatewayではなく、IGWを使う。NAT Gatewayは例え内部のリソースに公開IPアドレスが付与されても、外部発信のリクエストは許可されないように設計されており、これがIGWとの違い。

### SG設計
- EC2インスタンス
  - Inbound : 0.0.0.0/0, ポート 80 or 443, Allow
  - `検証シナリオと予測` のstep5にてOutbound許可ルールを削除する

### EC2
- 下記のユーザデータを設定
```sh
#!/bin/bash
yum install -y httpd
systemctl enable httpd
systemctl start httpd
echo "test" > /var/www/html/index.html
```

- SSHをSGのインバウンドルールで許可してサーバに入ってから上記のコマンド群を実行することも可。

### 検証シナリオと予測
- 1. VPC, Subnet, SG, rtb, IGW, EC2を各種起動
- 2. 外部機器からEC2インスタンスにcurl {EC2インスタンスのパブリックIPアドレス}にて挙動確認
  - NACLがデフォルト設定で全てを許可するのでcurl応答ありとなる
- 3. NACLのアウトバウンド許可ルール、ポート番号を1023以下に限定する
  - curl応答はなくなる
  - EC2インスタンスへのリクエストのソースはIGWとなるので、EC2からのレスポンス宛はIGWとなる
  - EC2までリクエストは届くが、レスポンスがNACLによってサブネットを出れない（IGWに届かない）ようになる
  - この手順では、NACLの設定のみ変更したので、NACLの挙動として確認ができる
  - この結果より、NACLはアウトバンドルールを変えただけでcurl応答がなくなったので、ステートレスであると確認ができる
- 4. NACLのアウトバウンド許可ルールのポート番号をすべて許可するように変更
  - curl応答がかえるようになる
- 5. EC2のSGのアウトバウンドルール 0.0.0.0/0を削除する
  - これでもcurlは成功する
  - この結果より、インバウンドルールで受け入れた通信はアウトバウンドルールで許可されていなくても外部機器へとレスポンスが届くので、SGはステートフルであることが確認できる

### セキュリティ設計
- EC2のSGは、curl通信のみを許容すれば事足りる。特定のユーザや企業のみからしかアクセスできないようにしたければIPアドレスで絞るケースもありそうだが、今回はany ipとする

### 可用性設計
- 今回は対象外

### コストの見積もり・意識した点
- EC2を使うのは運用コストの話が出てくる（とはいえ、ECSより柔軟性は増す）が、それは無視できるほど起動時間は短いと思われる。
- EC2インスタンスのスペックは最小限にする
  - 単なるcurlを最大でも10/min程度で返せればいいような実験内容なので、金額的コストを抑えるために
- NACLの挙動が確認できる最小限を意識して設計した
- EC2にパブリックIPアドレスを付与する（自動割り当てON設定）。でないと、その他設定が正しくても外部からのリクエストが届かない
