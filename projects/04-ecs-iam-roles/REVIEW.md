# レビュー: 04-ecs-iam-roles

## お題

- お題名: 04-ecs-iam-roles
- 種別: 設計課題
- レビュー日: 2026-07-17(設計レビュー)

## 総評

`01-vpc-network`で2回連続誤答していた「CloudWatch Logsへの書き込みはExecution Role/Task Roleどちらの担当か」を、今回は迷わず正しく判断できた。管理ポリシーに頼らずカスタムポリシーで最小権限を洗い出す進め方も最後までやり切れている。ただし、細部(HTTPとHTTPSの区別、DNS解決の要否、選定理由の記述の正確さ)では複数回の指摘・修正が必要だった。指摘した内容には毎回きちんと反応し、的外れな回答なく修正できている。

## 難易度感(次の出題調整に使う)

- この課題は今のレベルに対して: ちょうど良い
- 理由: 核心(ロール分担の判断)は迷いなく正解できたが、周辺の設計精度(ポート・DNS・コスト・用語の正確さ)を詰める段階では複数回のフィードバックが必要だった。「概念は掴めているが、実装レベルの精度に落とし込むには反復が要る」という現在地に合っている

## 観点別レビュー

### 設計

- ECS Task Execution Role(起動準備の担当)とTask Role(コンテナ自身の処理の担当)という分類軸を正しく適用し、ECRプル・CloudWatch Logs書き込み・S3書き込みの3処理を正確に振り分けられた
- 管理ポリシー(`AmazonECSTaskExecutionRolePolicy`等)に頼らず、AWS公式ドキュメントで実際に必要なAPIアクションを自力で洗い出せた
- 構成図で、ECR/S3/CloudWatch Logsを「VPCの外(Region内)」に正しく配置。セッション内で説明した内容を即座に図に反映できた

### セキュリティ

- SGが必要なのは(NAT Gateway/IGWにはSGが付与できないため)ECSタスクのENIのみ、という判断は正しい
- 初期のSG設計はポート80が不要に含まれ、DNS(53)のアウトバウンドが漏れていた。指摘後に両方修正し、DNSの宛先もインターネット全体でなくVPC内部のリゾルバ範囲に絞れた
- NAT Gatewayを直接SGのルールに指定しようとして詰まった際、「ルートテーブル(経路の決定)」と「SG(宛先ベースの許可)」が別レイヤーであることを説明した後、正しく整理し直せた
- IAMポリシーは`Resource: "*"`を避け、ECRリポジトリ・ロググループ単位までスコープを絞れている

### 可用性

- 今回は意図的にスコープ外(単発`run-task`、単一AZ)としており、お題の焦点(IAMロール設計)に合わせた妥当な判断
- AWSが2025年11月にリリースした「Regional NAT Gateway」について、その恩恵(複数AZへの自動追従)は単一AZ構成では発生しないと正しく整理し、既存のZonal NAT Gateway(`01-vpc-network`)の流用を選んだ

### 運用性

- `01-vpc-network`の既存VPC/NAT Gatewayを流用し、重複したインフラを作らない判断ができた
- VPCエンドポイント(PrivateLink)という代替案を検討した上で、今回はコスト・手間を優先してNAT Gateway継続利用を選択。検討過程を記録できている

### 保守性

- カスタム最小権限ポリシーは管理ポリシーより保守の手間が増えるが、それは今回の課題が意図する学習ポイントであり妥当なトレードオフ

### コスト

- 最終的な見積もり(合計約0.124ドル)は、NAT Gateway(時間課金+データ処理課金)、Fargate(vCPU/メモリ時間課金)を正しく計上し、IGW(無料であるため対象外)を除外、CloudWatch Logs(僅少だが対象として明記)も含められている
- 初稿ではIGWを誤って課金対象に含め、CloudWatch Logsが抜けていたが、指摘後に修正できた

### パフォーマンス

- 単発の短時間タスクのため大きな論点なし。スコープ外として扱って問題ない

### Terraform化した場合の改善点

- カスタムIAMポリシーJSONは、ハードコードした文字列ではなく`aws_ecr_repository.x.arn`や`aws_cloudwatch_log_group.x.arn`のようなリソース参照を使い、最小権限のスコープをリソース再作成時にも自動的に正しく保つこと

### AWS Well-Architected Framework 6本柱

- 運用上の優秀性: ロールの責務分離そのものが、誤った権限付与に気づきやすくする設計になっている
- セキュリティ: 管理ポリシー不使用・最小権限・リソーススコープ限定を徹底
- 信頼性: 今回は意図的にスコープ外。ECS Serviceとして常時稼働させる場合は再検討が必要
- パフォーマンス効率: 特筆すべき論点なし
- コスト最適化: NAT Gateway流用、VPCエンドポイントとの比較検討、正確なコスト試算ができている
- 持続可能性: 議論なし(この規模の学習用途では優先度低)

### 実務ならどう設計するか

- 本番で常時稼働するECS Serviceであれば、頻繁なイメージpull・ログ送信でNAT Gatewayのデータ処理課金がかさみやすく、VPCエンドポイントへの切り替えが妥当になるケースが多い。今回の判断(NAT Gateway流用)はあくまで単発の学習用検証だからこそ成立するという前提の違いを自覚できていた

## 理解できていること

- ECS Task Execution RoleとTask Roleの責務分担(CloudWatch Logsの書き込みがExecution Role側であること含む)。過去2回の誤答から格上げ
- SGは「自分のENI」に付けるものであり、相手側リソースがSGを持てるかどうかとは無関係という理解
- CIDR指定とSG参照(`referenced_security_group_id`)の使い分け基準
- NAT Gateway/IGWの課金体系(時間課金・データ処理課金・IGW自体は無料)

## 曖昧なこと

- HTTP(80)とHTTPS(443)の区別(AWS API通信は常にHTTPSのみ)。指摘されるまで確信を持てず「443 or 80」と書いていた。`01-vpc-network`から続く継続フォロー項目
- DNS解決の仕組み(VPC内部リゾルバへの問い合わせであり、インターネット全体への問い合わせではない)。指摘されて初めて理解した新規知識で、定着は未検証
