# 04-ecs-iam-roles

## 課題内容(メンターから提示された要件)

`01-vpc-network`では、ECS Task Execution RoleにAWS管理ポリシー(`AmazonECSTaskExecutionRolePolicy`)をアタッチしただけで済ませました。このポリシーは「ECRからのイメージ取得」と「CloudWatch Logsへの書き込み」の両方の権限を一括で含んでいるため、どちらの権限がどちらのロールの責務なのかを意識せずに動いてしまいます。

今回はこの管理ポリシーを使わず、**必要な権限をカスタムポリシーで洗い出し、Task Execution RoleとTask Roleのどちらに割り当てるべきかを自分で判断して実装する**ことがテーマです。

用意してもらいたいFargateタスク(ALB/ECS Serviceは不要。単発の`run-task`で確認できれば十分です)には、以下の3つの処理が発生します。

1. **コンテナイメージの取得**: パブリックの`nginx:latest`ではなく、自分のECRプライベートリポジトリに置いたイメージを使う(既存のnginxイメージをpull/tag/pushする程度でよい)
2. **アプリケーション相当の処理**: コンテナ起動後、S3バケットに何らかのオブジェクトを1つ書き込む(実際のアプリコードは不要。起動コマンドを`aws s3 cp`等のAWS CLI呼び出しに差し替えて代用してよい)
3. **ログの転送**: コンテナの標準出力をCloudWatch Logsに転送する(`awslogs`ログドライバー)

やってもらいたいこと:

- 上記1〜3それぞれに必要なIAM権限(APIアクション)を洗い出す
- それぞれの権限を「Task Execution Role」「Task Role」のどちらに割り当てるべきか、理由とともに判断する
- 判断に基づき、最小権限のカスタムIAMポリシーを設計・実装する(AWS管理ポリシーは使わない)
- 実装後、意図的にどちらか1つの権限を欠いた(または逆のロールに割り当てた)状態で一度起動し、実際に発生するエラー(タスクの停止理由、CloudWatch Logsに残るエラーメッセージなど)を観察する。どちらのロールの権限不足かを、実機の情報だけから切り分けられるか確認すること

設計がまとまったらAWSコンソールで構築し、上記の権限不足の実機確認を行ったうえで、Terraformでコード化します。

## 前提・制約

- `01-vpc-network`で構築したVPC(プライベートサブネット)・ECSクラスターを流用してよい。ネットワーク設計のやり直しは不要
- ALB/ECS Serviceは不要。`aws ecs run-task`による単発実行で確認できれば十分(スコープを絞り、IAMロールの権限設計に集中する)
- ECRリポジトリは新規作成が必要
- コスト: Fargateタスクは単発・短時間の起動のみなので数十円程度。確認が終わったタスク定義・ECRイメージ・S3オブジェクト等は速やかに整理すること

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
| NAT Gatewayとインターネット間の通信を可能にするため | IGW | VPCエンドポイントによってネットワーク通信を用いずに実装も可能だが、今回のお題において過剰設計であると判断し、IGWを選定 |
| ECSをセキュリティ上の観点からプライベートサブネットに配置したままECR・Cloud Watch Logsとインターネット通信できるようにするため | NAT Gateway | リージョナルNAT Gatewayの方が可用性を維持しながら管理を楽にできるが、運用コストを考えるような話ではないため、従来のNAT Gatewayを選定。今回は単一AZで問題ないと判断し、リージョナルNAT Gatewayにしても運用コストの恩恵は小さいと判断 |
| コンテナ起動 | ECS | 今回は指定があったため選定したが、Webサービスなどの長時間稼働が求められる、かつOS管理などの運用コストを抑えたい場合の選択肢 |
| コンテナ起動に必要なイメージの保存先 | ECR | 他の代替サービスを知らない |
| コンテナからデータをアップロード | S3 | 今回は指定があったため選定したが、PDF、動画、画像などの非構造化データで容量が多くなるようなケースにおいて選定する際の候補 |
| コンテナ起動時やコンテナで実行されるAPIのログ収集 | Cloud Watch Logs | コンテナの標準出力などのログを収集するのに適しているため |

### 権限設計(Task Execution Role / Task Role)

| ロール | アクション | リソース | 理由 |
|---|---|---|---|
| Task Execution Role | ecr:GetAuthorizationToken | * | ECRレジストリへのログイン認証。リポジトリ単位で絞れないアクションのため*を使用 |
| Task Execution Role | ecr:BatchCheckLayerAvailability | 特定のECRリポジトリ | レイヤーが取得可能な状態かを確認してからダウンロードURLを要求する |
| Task Execution Role | ecr:GetDownloadUrlForLayer | 特定のECRリポジトリ | コンテナイメージのレイヤーデータをS3からダウンロードするための一時的な署名付きURLを取得するため |
| Task Execution Role | ecr:BatchGetImage | 特定のECRリポジトリ | コンテナイメージのメタデータを取得するため |
| Task Role | s3:PutObject | 特定のs3バケット | s3に書き込みを行うため |
| Task Execution Role | logs:CreateLogStream | 特定のロググループ | ログを記録するためのログストリームの作成をするため |
| Task Execution Role | logs:PutLogEvents | 特定のロググループ | ログを記録するため |

### ルートテーブル設計
- ECS Subnet
  - local：明示的に設定は不要
  - 0.0.0.0/0 NAT Gateway
- NAT Subnet
  - local：明示的に設定は不要
  - 0.0.0.0/0 IGW

### SG設計
- ECSのSG
  - Outbound：0.0.0.0/0 443(TCP)
    - ECRからイメージをプルしてくる、S3にアップロードする、Cloud Watch Logsにログを送信する、はいずれもインターネット経由で行うため、これらを許可するためのルール
  - Outbound:10.0.0.0/16 53(UDP)
    - S3,ECR,Cloud Watch Logsへ通信する際に必要な名前解決

### セキュリティ設計
- 最小権限の原則に従って、IAMロールの定義を行った

### 可用性設計
- 今回は対象外

### コストの見積もり・意識した点
- NAT Gateway
  - 処理データ1GBあたり0.062ドルだが、今回はデータが1GBにも満たないと想定されるため、ほぼ0として見積もって良い
  - 起動時間当たり0.062ドル/1h、1時間程度で実験は終了すると想定し、0.062ドル
  - 合計約0.062ドル
- ECS(Fargateで起動)
  - vCPU/1hあたり0.05056ドル
  - GB/1hあたり0.00553ドル
  - 1vCPU、2GB、1時間起動想定
  - 合計約0.062ドル
- ECR（プライベートリポジトリ）
  - データ受信は0.00/GBのため、0ドルとする
  - データ送信は最初の9.999TB/月は0.114/GBだが今回は軽量であるため、0とする
  - 合計0ドル
- S3
  - ストレージはS3スタンダードとする。最初の50TB/月は0.025ドル/GBで、今回アップロードするものはかなり軽量であるため、0ドルとする
  - 合計0ドル
- Cloud Watch Logs
  - スタンダード収集は1GBあたり0.76ドルだが、収集されるログはトータルでも軽量のため、0ドルとする
  - 合計0ドル
- トータル0.124ドル
