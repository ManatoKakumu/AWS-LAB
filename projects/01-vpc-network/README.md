# 01-vpc-network

## 課題内容(メンターから提示された要件)

以下の要件を満たすVPCを設計する。**この段階ではコードや構築の話は持ち込まない。まず設計をまとめてレビューを受けること。**

- 3層のネットワーク分離(例: Web層/アプリ層/データ層、あるいはpublic/private-app/private-data等、自分が適切と考える区切りで良い。層の呼び方・境界線をなぜそこに引いたか説明できるようにしておく)
- 2〜3AZにまたがる高可用性構成
- インターネットゲートウェイ(IGW)とNAT Gatewayを適切に配置し、**それぞれの役割分担**を設計上明記すること
- ルートテーブル設計(どのサブネットがどのルートテーブルに紐づき、どこへどう通信が流れるか)

特に以下の観点は意識して設計し、REVIEWで説明を求める:

- NAT Gatewayを1つだけ(単一AZ)に置く場合と、AZごとに1つずつ置く場合とで、可用性・コストにどう違いが出るか。自分の設計ではどちらを選んだか、理由とともに説明できるようにしておくこと

## 前提・制約

- 小〜中規模のWebサービスを想定する(具体的なユーザー数・トラフィック規模の仮定は自分で置いてよいが、README上に明記すること)
- チーム体制: 運用を兼任する小規模チーム
- 予算: 学習用AWS費用は月数千円程度まで許容(NAT Gatewayは時間課金であることを踏まえて設計・検証すること)
- リージョン: ap-northeast-1(既定。変更する場合はここに明記)
- 進め方: 設計 → メンターによる設計レビュー → (合格後)AWSコンソールで構築 → 同じ構成をTerraformでコード化、の順で進める

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
|外部ネットワークとVPCの接続口|IGW|この用途に他の有力なサービスはないはず|
|パス/ホストベースルーティングにてAP層やWeb層へのリクエスト先変更。負荷分散。HTTPS通信の終端|ALB|HTTP対応かつ推奨されているLBであるため|
|プライベートサブネットを直接IGWへのルートを持たせると外部の世界につながってしまいセキュリティリスクとなるのを防ぎつつ、プライベートサブネット配置のインスタンスから外部通信を実現させたいため|NAT Gateway|NATインスタンスと違って、マネージドサービスであり、特別な設定（OS管理など）が不要であるため|
|WebおよびAP層の実行環境|ECS|EC2のように、OS管理などの用途は不要であると判断したため、マネージドサービスを選択。Lambdaはそもそも、最大実行時間15分という制限があって短めの処理用のサービスであり、Webアプリケーションの用途には不向き|
|構造化データ管理|RDS|リレーショナルデータベースに対応しているマネージドサービスであるため|

### ルートテーブル設計
- AZ1のCIDRブロックとして表記するが、AZ2も設定は同様であり、CIDRブロックの数字をAZ2のものに置き換える
- 同一VPC内はlocalにて解決できるため省略するが、その他に追記が必要なもののみ下記に記載
- ALB
  - 0.0.0.0/0 IGW
- NAT Gateway
  - 0.0.0.0/0 IGW
- AP層
  - 0.0.0.0/0 NAT Gateway

### セキュリティグループ設定
- ALB
  - Inbound : 0.0.0.0/0 ポート番号80 or 443
  - Outbound : Web層のSG
  - Outbound : AP層のSG
- Web層
  - Inbound : ALBのSG
  - Outbound : 0.0.0.0/0 NAT GatewayのSG
- AP層
  - Inbound : ALBのSG
  - Outbound : DB層のSG
  - Outbound : 0.0.0.0/0 NAT GatewayのSG
- DB層
  - Inbound : AP層のSG

### セキュリティ設計
- 必要最小限の権限に絞る
- NAT GatewayによってWeb3層アーキテクチャは外部から保護

### 可用性設計
- マルチAZ構成とすることでAZ単一障害点にならないように、高可用性を考慮

### コストの見積もり・意識した点
- ASを設定し、不要なコンテナ稼働を抑える
- コストアラートの段階的設定や通信手段、人による単一障害点を作らないように注意してコストアラートを設定すべき
  - 通信手段としてslackを選んだがslackに障害が発生していた場合にアラートが飛ばないので、よく見る連絡手段複数を設定するとよい
  - 1人だけしかアラートが見れない状態だと、その人が気づかない可能性があるのでグループベースでの通知が良い
- SGはIPアドレス対象にすると、ASで作成されたインスタンスからの接続拒否や、不必要にCIDRブロックを広げることにつながるため、SGとして指定
- ECSのタスク実行ロールではなく、タスクロールにIAMロールを付与するように注意すべき
  - タスク実行ロール：コンテナ環境の準備に必要になるロール。ECRからのイメージプルや参照など
  - タスクロール：コンテナが何かしらのAWSリソースを使う際に必要なロール
- NAT Gatewayを単一AZに配置する構成だと、AZで障害が発生した際にAP層のメール送信処理など外部へのリクエストを飛ばせなくなり、サービスとして致命的になる。NAT Gatewayは時間課金であり、複数たてるとコストは高くなるが、それよりも可用性を優先すべきであると判断し、マルチAZ構成とした
- 正直、トラフィックやユーザー数に応じてどのように何を変えていけばいいのかも、相場も全くわからないので、想定したものでいいといわれても、という感じであった。小-中規模ならば月間10,000ユーザー、最大100/1minトラフィック程度でしょうか
- ALBでHTTPS終端とするのは、複合処理をWebサーバなどに任せて負荷を重くしないためである。本来であれば証明書やACMが必要だが、今回は省略した。これはのちの課題にて実装予定としたい
- 本来ならばRDSの最終スナップショットはとっておくべきだが、今回は学習用ということでコスト面も考慮し、取得しない

## わからなかったこと・迷ったこと
- ECS/ALB関連の用語理解に苦しんだ(詳細はREVIEW.md参照)
- 実際に起きたトラブル:
  - SGにポート443ルールを追加する際、Inbound/Outboundを逆にしてしまった
  - ALB↔Web/AP間のSGルールがポート0になっており、実トラフィックが通らなかった
  - Execution Roleに`logs:CreateLogGroup`権限が無く、タスク起動に失敗した
  - 削除し忘れた旧ECSサービスが二重稼働していた
