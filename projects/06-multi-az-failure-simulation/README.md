# 06-multi-az-failure-simulation

## 課題内容(メンターから提示された要件)

`05-ecs-autoscaling`では、スケーリング挙動の確認を主目的としていたため、ECSタスクの配置は単一AZに限定し、可用性は重視しない設計をあえて選んだ(NAT Gatewayも単一AZ配置)。今回はその制約を外し、**可用性そのものを主目的とした設計**に切り替える。

やってもらいたいこと:

1. ECSサービスのタスクを複数AZ(最低2AZ)に分散配置する構成に設計し直す。あわせて、NAT Gatewayを各AZに配置するかどうかを、可用性とコストのトレードオフとして自分で判断し、理由とともに言語化する
2. 「1つのAZが丸ごと利用不可になった」状態を、実機で意図的に再現する方法を自分で設計する(方法は問わない。例えば対象AZのサブネットのルートテーブルを壊す、NACLで遮断する、SGで対象AZのタスクへの通信を止める、など複数の選択肢がありうる。それぞれの再現方法が実際のAZ障害とどれだけ近いか/遠いかも考えること)
3. 障害を実際に起こす前に、何が起きるはずかを予測として書く(ALBのヘルスチェックがどのタイミングで異常を検知するか、ECSサービスがどう新しいタスクを配置しようとするか、ユーザーから見たダウンタイムはどの程度発生しうるか)
4. 実際に障害を再現し、CloudWatchメトリクス・ECSサービスのイベント履歴・ALBターゲットグループのヘルス状態から、予測と実際の挙動を比較する
5. 観察が終わったらTerraformでコード化する

## 前提・制約

- `01-vpc-network`/`05-ecs-autoscaling`で構築したVPC・ALB・ECSクラスターの構成をベースにしてよい。ただし今回はAZ分散が主目的のため、「挙動確認が目的だから単一AZでよい」という05での判断はそのまま流用できない
- コスト: NAT Gatewayを複数AZに配置する場合、時間課金が単純計算で倍になる。確認が終わったら速やかにdestroyすること
- 実験中はALBやECSタスクへの通信を意図的に壊すため、確認が終わったら必ず正常状態に戻す(または速やかにdestroyする)こと

## 環境情報

- Terraformバージョン:v1.15.4
- AWSプロバイダーバージョン:v5.100.0
- リージョン: ap-northeast-1(既定。変更した場合はここに明記)
- AWSリソースの状態(コンソール構築分): 破棄済み
- Terraformの状態: apply → 障害注入実験 → destroy済み(AWS CLIで全リソース削除を確認)

## 設計

### 構成図

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
| イメージをプルしてくる際のECS発信の通信の出口、およびレスポンスとして機能 | IGW | 代替サービスがない |
| コンテナ起動時に使うイメージをプルしてくる際に、ECSを配置するプライベートサブネットがNAT Gatewayを経由してインターネットからイメージをプルする | NAT Gateway | NATインスタンスはOSの管理などが必要になるが、OSなどを柔軟に設定したい用途がないのでマネージドサービスを使い、運用負荷を下げるため |
| 外部からのリクエストをECSタスクへ振り分ける | ALB | Webサイトを想定しているため、NLBではなくALBを選定。今回のALBはinternalスキームとして構築する。理由は外部からの実接続テストを行わないため |
| コンテナを起動し、実際のアプリケーション処理(Webアプリなど)を行う | ECS | EC2などでも達成できるが、インフラ管理の容易性などから選定 |
| メトリクスやタスクの状態を確認するため | CloudWatch | 代替サービスがない |

### NAT Gatewayを各AZに配置するか
- 本番環境での運用などにおいては、コストよりも可用性を維持すべきケースが多いと思われるが、今回は挙動確認が目的であるのでコスト優先で、単一AZにNAT Gatewayを配置することにした
- 今回は疑似的に片方のAZに障害を起こすが、その方法はECSを配置するサブネットに付与するNACLのInboundルールでhttp通信を拒否させる方法である。コンテナ起動時にイメージをプルしてくる際はhttps通信なので、疑似的な障害発生時にも影響を受けることはない

### ルートテーブル設計
- ALB Subnet
  - local：デフォルトで設定されるため、自身による設定不要
- NAT Subnet
  - local：デフォルトで設定されるため、自身による設定不要
  - 0.0.0.0/0 IGW：インターネットへ通信する際に使うルート
- ECS Subnet
  - local：デフォルトで設定されるため、自身による設定不要
  - 0.0.0.0/0 NAT Gateway：イメージをプルしてくる際にNAT Gatewayを経由する際に使うルート

### SG設計
- ALB
  - Inboundなし
  - Outbound ECS-SG 80ポート：ALBからECSタスクへのリクエスト送信
- ECS
  - Inbound ALB-SG 80ポート：ALBからECSタスクへのリクエスト送信
  - Outbound 10.0.0.0/16 UDP 53ポート：イメージをプルしてくる際の名前解決
  - Outbound 0.0.0.0/0 TCP 443ポート：イメージをプルしてくる際の実際の通信

### IAM設計
- タスクロール
  - 障害を疑似的に発生させたほうにはALBがリクエストを送信しないようになることを確認するのが目的であり、タスクの中に入ったり、ほかのリソースにアクセスすることはない
  - なし
- タスク実行ロール
  - Docker Hubからイメージをプルしてくるため、ログ関連のみの権限で十分
  - logs:CreateLogStream 特定のARN
  - logs:PutLogEvents 特定のARN

### NACL設計
- NACLはデフォルトのものを使用する
- 例外で、ECS Subnetに紐づけるNACLとして異常系（疑似的に障害を発生させるためのもの）のものを一つ用意する
  - Outbound ルール番号1 0.0.0.0/0 -1 許可
  - Inbound ルール番号1 0.0.0.0/0 TCP 80ポート 拒否
  - Inbound ルール番号2 0.0.0.0/0 -1 許可

### 実験手順
- どのサブネットもデフォルトのNACLとする
- ヘルスチェック設計については05のものを流用する
  - 30秒ほどで異常であると判断される
- ECSサービスにて、desired countを4に設定する
- 2つのAZでタスクが起動するのを確認する
- 疑似的に片方のAZのみで障害を発生させる
  - 片方のECS SubnetのNACLのみを異常系のNACLに付け替える
  - ECSへのインバウンド通信TCPによる80ポートを使った通信が拒否されるようになるので、ヘルスチェックが失敗するようになる
- この実験により、下記のようになると予想
  - 疑似的な障害により、片方のAZではヘルスチェックが失敗するようになるので、ALBがリクエストを送信しなくなるが、もう片方のAZではヘルスチェックが継続的に成功するため、サービス全体としては落ちずに可用性が保てる
  - ECSサービスは疑似的な障害であるがゆえに、AZが落ちたとは認識せず、継続的に障害が発生したAZにもタスクを起動させるようにECSエージェントに起動命令を出す

### セキュリティ設計
- 今回は外部からの通信は不要であるため、ALBもインターネットからのリクエストを受け付けないように設定

### 可用性設計
- ECSのマルチAZ配置は、片方のAZで障害が発生しても、残りのAZでは稼働するため、サービス全体が停止することはなく、可用性を高めることが可能
- ALBに関しては、サービスの制約上、複数のAZを指定する必要があるため、マルチAZ配置となっている
- 一方で、NAT Gatewayは単一AZに配置しているが、これはコストを考慮してこのような構成にしている

### コストの見積もり・意識した点
- ALB
  - 0.0243/Application Load Balancer/時：1台起動、1時間と想定し、0.0243ドル
  - 0.008/LCU/時：通信量はかなり少ないので0として見積もる
  - 合計0.0243ドル
- NAT Gateway
  - USD 0.062/時：1台起動、1時間と想定し、0.062ドル
  - USD 0.062/GB：通信量はかなり少ないので0として見積もる
  - 合計0.062ドル
- ECS
  - USD 0.05056/vCPU/時：1vCPU、1時間と想定し、0.05056ドル
  - USD 0.00553/GB/時：2GB、1時間と想定し、0.01106ドル
  - desired countは4とする
  - 合計0.24648ドル
- 異なるAZ間の通信
  - 0.01 USD/GB：NAT GatewayとECS間は異なるAZ間通信が発生し得るが、無視できるほど小さいと判断し、0ドルとする
  - ALBとタスク間の異なるAZ間通信においては通信料は発生しないので0として見積もる
  - 合計0ドル
- Cloud Watch
  - ログの量もかなり少なく、最初の5GB分は無料枠に入るため0として見積もる
  - 合計0ドル
- 合計0.33278ドル

## 実装

### AWSコンソールでの構築記録
- リソースなどを構築後、実験手順に従い、挙動を確認
- 正常時は両AZに均等になるようにタスクを配置しており、障害を発生させた最初のうちも均等に配置させようとしていた
- しかし障害発生から5分ほど経過すると、正常なAZにより多くのタスクを起動させようとするようになった
  - おそらくECSサービスによって障害発生AZにタスクを起動させなくなるようにECSエージェントへ命令したのだと思われるが、事実確認はしていない
  - ドキュメント上はタスク数ベースの判断であり、むしろ1cへの追加起動を促すはずの仕組みなので、観察された偏りの直接的な説明にはならない。正確な原因は未解明だったが、後述のTerraform再実験でAZ Rebalancing機能(`availability_zone_rebalancing`)の存在に気づき、原因の仮説を特定できた

### Terraform実装

- コード: `06-multi-az-failure-simulation.tf`(単一ファイル)
- `terraform plan`結果: `Plan: 36 to add, 0 to change, 0 to destroy`(設計通り。エラーなし)
- `terraform apply` → 正常系(NACL未紐づけ)で両AZに均等にタスクが配置されることをAWS CLIで確認 → `aws_network_acl.abnormality`の`subnet_ids`を有効化して再apply → 障害注入 → `terraform destroy`まで実施し、全リソースの削除をAWS CLIで確認済み

#### AZタスク偏りの原因調査(Terraform再実験で判明)

`terraform plan`の出力に`aws_ecs_service`のデフォルト属性として`availability_zone_rebalancing = "DISABLED"`が表示されたことから、AWSに「稼働中の健全なタスクも含めてAZ間バランスを継続的に監視・是正する」機能(2024年追加のAZ Rebalancing機能)が存在し、これがデフォルトでは無効であることが分かった。

AWS CLIで障害注入後の`RUNNING`/`STOPPED`タスクを時系列で取得したところ、以下が確認できた。

- `STOPPED`タスク14件すべてが`1c`(障害注入AZ)。`1a`のタスクは一度も置き換えられていない
- 当初2:2だった配置が、`1c`の2タスクが同時に異常判定された置き換えイベント(1回で2タスクを新規配置)を境に3:1へ偏り、以後3:1で固定された

以上から、以下の仮説に到達した(AWS内部アルゴリズムの完全な仕様は非公開のため、複数の観察結果と整合する仮説という位置づけ)。

- ECSは新規タスクを配置する際、対象サブネットのうち「現在の実行数が少ない方」を優先する
- 上記のルールにより、同時に2タスクを置き換える場面では1a・1cに1個ずつ配置され、既存のバランスが崩れる
- 崩れた後は、AZ Rebalancing機能が無効なため健全な`1a`のタスクは動かされず、`1c`の1タスク分だけが繰り返し置き換えの対象になり続けるため、3:1のまま固定される(2:2に戻ることも、4:0になることもない)
