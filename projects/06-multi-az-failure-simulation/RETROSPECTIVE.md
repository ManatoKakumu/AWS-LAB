# 振り返り: 06-multi-az-failure-simulation

## お題

- お題名: 06-multi-az-failure-simulation
- 実施日: 2026-07-23(出題)〜2026-07-27(Terraform実装・振り返り)

## できたこと

- 設計・AWSコンソール構築は`05-ecs-autoscaling`の構成をベースに、ALBのinternal化・ECSの2AZ分散・NAT Gatewayの単一AZ残し・障害注入用NACLの追加、という今回固有の差分を正しく組み込めた(本人評価: ただし`05`との類似度が高い課題だった点も影響している)
- Terraform実装では、既存の`for_each`構文をマルチAZ構成のサブネット定義にそのまま転用できた
- `terraform plan`(36 to add, 0 to change, 0 to destroy)→`apply`(正常系確認)→NACL有効化での再`apply`(障害注入)→`destroy`という一連の流れを、AWS CLIでの状態確認を交えながら完遂した
- 障害注入後の挙動をAWS CLI(ALBターゲットヘルス、ECSサービスイベント、タスクの時系列)から観察し、README.mdの事前予測(ALBが約30秒で異常検知、ECSは障害AZへの配置を諦めず繰り返し試行)との一致を確認した
- AWSコンソール構築時に「原因未解明」のまま持ち越されていた「AZタスク配置の偏り(2:2→3:1で固定)」について、`terraform plan`に表示された`availability_zone_rebalancing`という属性名をきっかけに、AWS CLIで取得した実データ(STOPPEDタスク14件すべてが障害注入AZに集中、等)から一貫した仮説(新規配置は実行数が少ないAZを優先/健全なタスクは動かされない)に自力で到達できた
- コピペミス(下記)を指摘された瞬間、自分で「コピペ時の修正忘れ」と診断できた。`05`の振り返りで合意した「見直しの習慣」が機能した最初の実例
- `for_each`構文の再指摘(1回)を経て、正しい参照方法(`aws_subnet.ecs["az2"].id`)を一度の説明で習得した
- ALB/ECSサービスの役割分担について、ECS側はイベントログを根拠に正確に説明できた

## できなかったこと

- 「AZタスク配置がなぜ3:1で固定されるか」の理解に時間がかかった。当初は「ログだけでは推測できない」と結論を急いでしまったが、対話を通じて「3:1で固定される理由」と「4:0にならない理由」が同一のルール(新規配置は実行数が少ないAZを優先/健全なタスクは動かされない)で説明できることに気づけた。「わからない」と判断する前に、手持ちのデータをもう一段掘る余地があった

## 自分では理解しているつもりだったが、レビューで指摘されたこと

- `aws_ecs_service`の`network_configuration.subnets`が`aws_lb.alb`のサブネットを参照していた。コピペ後に一度確認したつもりだったが、確認漏れが発生した(`01`から続く「コピペ時の見直し漏れ」パターンの5回目の再発)
- 記録を見ない理解度チェックで、ALBのヘルスチェック対象IPを「パブリックIP」と説明し、プライベートIPと逆に理解していた(EIP/プライベートIPの混同は`01`〜`04`から継続する項目で、今回も再発。ただし指摘後は`assign_public_ip = false`の設定と結びつけて即座に自己修正できた)
- `aws_network_acl`の`subnet_ids`で、`for_each`リソースをキー指定なしで参照する誤りが再発した(`03-rds-scaling`で一度指摘済みの構文)

## 次に同じ種類の課題が出たら気をつけること

- コピペ後は「動くかどうか」だけでなく「この参照先は今回の文脈で本当に正しいリソースか」を一行ずつ見直す
- パブリック/プライベートIPの区別に迷ったら、都度`assign_public_ip`(またはEIPの有無)の設定に立ち返って確認する
- 一見「原因不明」に見える現象でも、手持ちのログ・データの中で一貫した説明ができないか、結論を急がずもう一段掘ってみる

## CURRENT_LEVELへの反映

- 格上げ: AZ障害注入実験の設計〜実施〜観察〜(今回は)原因調査までを一通り自走できた。ALBの異常検知とECSサービスのタスク配置継続が別主体・別タイミングの動作であることは、実機ログを根拠に正確に説明できるレベルに到達
- 新規知見として格上げ: ECSのAZ Rebalancing機能(`availability_zone_rebalancing`)の存在と、無効時に「一度崩れたAZ間バランスが自己修復されない」理由の理解。前回セッションで「未解明」だった論点を、自力の調査で解消した
- 曖昧なまま/再確認が必要:
  - EIP(パブリックIP)とプライベートIP(awsvpcモードの専用ENI)の混同(`01`〜`04`から継続、今回5回目相当の再発)
  - `for_each`で作ったリソースから単一要素を参照する構文(`03`から継続、再発2回目。ただし指摘後は一度で習得できており定着傾向にある)
  - 「コピペ実装時の値の見直し漏れ」(`01`から継続、5回目の再発。ただし今回は指摘された瞬間に自分で「コピペミス」と診断できた点は過去との違いで、`05`の対策合意が機能し始めている兆し)

## 次回への持ち越し・気になったこと

- 「原因不明」と判断する基準を、もう少し慎重にする(データをもう一段掘ってから判断する)という視点は、今回の対話で得られた具体的な教訓として次回以降のトラブルシューティング課題で意識する
