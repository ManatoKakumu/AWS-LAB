# 07-elasticache-caching

## 課題内容(メンターから提示された要件)

`03-rds-scaling`では、DBの読み取り負荷を分散する手段として「リードレプリカ」を扱った。今回はもう一つの代表的な負荷軽減手段である**キャッシュ(ElastiCache)**を導入し、両者の目的差分を設計レベルで整理してもらう。

やってもらいたいこと:

1. ECS(アプリ層)→RDS(DB層)という既存構成(`01`/`03`/`05`/`06`をベースにしてよい)の間に、ElastiCache(RedisまたはMemcachedのいずれかを選び、選定理由を言語化する)を配置する設計をする
2. 「リードレプリカ」と「キャッシュ」は、どちらも読み取り負荷を減らす手段だが、目的・データの新しさ(整合性)・向いているユースケースがそれぞれ異なる。この差分を、抽象論ではなく今回の具体的なアプリケーション(何をキャッシュするか)に即して説明する
3. キャッシュ戦略を設計する: 何をキー/値としてキャッシュするか、TTL(有効期限)をどう決めるか、DBの値が更新された場合にキャッシュをどう追従させるか(Write-through/Cache-asideなど、方式を選び理由を述べる)
4. キャッシュ自体が落ちた/使えない場合にアプリケーションがどう振る舞うべきか(フェイルオープン: DBに直接見に行く/フェイルクローズ: エラーを返す)を設計判断として決める
5. セキュリティ・可用性・コストの観点も他のお題と同様に整理する

## 前提・制約

- `01-vpc-network`/`03-rds-scaling`/`05-ecs-autoscaling`/`06-multi-az-failure-simulation`で構築したVPC・ECS・RDSの構成をベースにしてよい
- ElastiCacheはノードタイプ次第で時間課金が発生する。設計・レビューが済んだらAWSコンソールでの構築に進み、確認が終わったら速やかに破棄すること
- 今回はアプリケーションコード(実際のキャッシュ読み書きロジック)の実装までは求めない。インフラ設計(ElastiCacheクラスターの配置・セキュリティグループ・パラメータグループ等)と、キャッシュ戦略の設計判断が主目的

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
| APIやフロントコードをデプロイする | ECS | 今回はECサイトを想定しており、一般的なものに関しては、OSまで柔軟に設定する用途がないので、マネージドサービスを使うことで運用コストを低減させるため |
| セッション情報および商品紹介ページに使う説明文のインメモリキャッシュ | Elastic Cache | 読み取り頻度が高く、書き込み頻度が少ないデータの読み取りリクエストのレイテンシを下げるため |
| 商品情報、ユーザ情報、などのデータを保存 | RDS | ECサイトではリレーショナルデータベースが適切であること、フェイルオーバーの所要時間が厳しくないのでAuroraではなくRDSとした |

- Elastic CacheのエンジンとしてRedisを選定
  - 可用性向上のため、マルチAZ構成のプライマリ - スタンバイ構成を選択したいため
  - 将来的にインメモリで管理したい情報が増えても、データ型がstring型のみに縛られず、柔軟性が高いため
- Elastic CacheはマルチAZ構成をとる
  - 高可用性を実現するため
  - プライマリが障害などで落ちても、スタンバイにフェイルオーバーすることで、管理対象のデータへの読み取りリクエストがRDSのプライマリへの負荷を高めることを防ぐ目的がある

### Elastic cacheとリードレプリカの違い
- どちらも読み取り負荷を下げる効果があり、結果としてDBプライマリインスタンスなどの負荷を下げるという効果があるのは同じだが目的が異なる
  - Elastic cache：揮発性メモリのため、落ちるとデータが消えるため、永続的に保存したいユーザの個人情報などの保存には向かない。一方で、DBへアクセスする場合と比べてレイテンシが下がるので、頻繫に参照されるが、更新頻度は低いものを保存するのに向いており、セッション情報や商品紹介ページに使われる文字データなどが該当する。
  - リードレプリカ：プライマリインスタンスへの読み取り負荷を低減する際に効果的であり、永続的な情報も含まれているため、キャッシュへの保存には向かない情報の読み取りリクエストに大きな負荷がかかっている場合に追加すると効果が見込まれる
  - 単純なキー参照によってデータ取得したい場合はElastic cache向きで、複雑なクエリ（条件）絞り込みではリードレプリカが適切
  - Elastic cacheはアプリケーションの実装やTTLの設定によっては、古い間違ったデータが参照される可能性があるのでこれを許容できることが重要であり、リードレプリカは非同期でレプリケーション処理はされるがその遅延は基本的に無視できるほど小さいので古いデータ参照ケースはあまり考えられない

### キャッシュ戦略
- キャッシュ対象データ
  - セッション情報と商品紹介ページに使われる文字データ（価格、紹介文など）は読み取り頻度は高いものの更新頻度は低いため、有効
- TTL設定
  - セッション情報：ユーザの滞在時間の分布などがわかるのであれば、その時間に10分ほど余裕を持たせたくらいの感覚に設定する。長期で記憶しておくと、セッション乗っ取り被害のリスクや、保存コストが高くなるなどが考えられるため、不必要に長時間にTTLを設定するのはおすすめされない
  - 商品紹介ページ：仮で1時間とする。データ更新時にキャッシュキーの消し忘れで誤った情報が表示される時間としてどれくらい許容されるのか、という観点で決める
- DBの値が更新された場合のキャッシュ追従について
  - キャッシュアサイド戦略を採用
  - キャッシュ管理対象のデータが更新された際のレイテンシ増加を防ぐ目的
  - 仮にキャッシュキーの削除を忘れた場合もTTLによって自動的にキャッシュからデータが削除され、時間が経過すればDBとの不整合がなくなる（ただし、緊急時に備え、手動で消せるようにする必要もある）

### キャッシュが落ちた場合
- DBへリクエストを送信する
  - キャッシュが落ちることによる影響は、キャッシュ管理対象のデータへの読み取りリクエストのレイテンシが増加するのみであり、アプリケーションを落とすほどの大きな出来事ではない
  - なので、読み取りリクエストによる負荷の増加は許容し、サービス継続を優先事項とする
  - ただ、キャッシュが落ちた際、あるいはDBプライマリインスタンスへのI/Oなどに閾値を設定しておき、アラート設定することで、検知し、すぐにリードレプリカの追加ができる体制を事前に整えておくことは重要である

### 可用性設計
- Elastic cacheはマルチAZ構成とする
  - プライマリのAZ障害時にフェイルオーバーすることで、RDSプライマリインスタンスへの一時的な読み取りリクエストが集中することによる負荷を避ける可能性を向上させる目的
  - コストがRDSと比べて少ない、というのも一つの決定要因
- RDSのリードレプリカは追加しない
  - あくまで初期段階では、という話になるが、かりにElastic cache対象外のデータの読み取りリクエストによる負荷が大きければリードレプリカの追加を検討する
  - Elastic cacheに比べてコストが高い

## わからなかったこと・迷ったこと
- Elastic cacheについて
  - インメモリキャッシュで、キャッシュアサイドとライトスルー方式があるが、いずれもアプリケーションコードをどのように定義するかの話であり、AWSでモードのようなもので指定するものではない
  - キャッシュアサイドはDB更新時にキャッシュキー指定で更新したものを削除するが、忘れてもTTL切れによってキャッシュとDBの不整合は解消されるが、DB更新処理を記載し忘れると、更新したはずのデータが更新されていないことになる点に注意
  - ライトスルー方式は更新時にキャッシュとDB両方を更新する方式で、データ不整合を許容できない場合などに用いられるが、そもそもアプリケーションコードの実装に左右される要素であるてんは注意
  - キャッシュが不整合を超す可能性があるので、書き込み頻度が少ない、多少不整合のあるものでも構わない、複雑な条件（クエリ）による絞り込みを必要としないものなどが管理対象候補としてあげられる、また読み取り頻度の高いものでなければキャッシュを導入する効果は薄くなる
  - リードレプリカやマルチAZスタンバイ構成など、用途を自由に選択できる
  - キャッシュが落ちると、これまでキャッシュで対応していた読み取りリクエストがDBプライマリインスタンスに向き、負荷が急上昇する可能性がある
- TTLの決め方について
  - データの鮮度が新鮮でない可能性があり、それがどれくらい許容されるものであるのか、という判断のもと決める
  - 別件だが、念のためTTL切れを待たずに即座にキャッシュ削除してDBから読み込ませることでキャッシュとの不整合を無くす手段も持ち合わせておくべき
- SGの設定について
  - そもそもSGはENIに付与するものであり、ENIを独自で管理することができる、すなわちSG付与が可能ならば、レプリケーション処理通信を許可するルールの追加が必要で、Elastic cacheは必要だが、RDSのマルチAZ構成においては、SGで許可しなくて良い（というよりできない）
