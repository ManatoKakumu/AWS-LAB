# 07-elasticache-caching

## 課題内容(メンターから提示された要件)

`03-rds-scaling`では、DBの読み取り負荷を分散する手段として「リードレプリカ」を扱った。今回はもう一つの代表的な負荷軽減手段である**キャッシュ(ElastiCache)**を導入し、両者の目的差分を設計レベルで整理してもらう。

やってもらいたいこと:

1. ECS(アプリ層)→RDS(DB層)という既存構成(`01`/`03`/`05`/`06`をベースにしてよい)の間に、ElastiCache(RedisまたはMemcachedのいずれかを選び、選定理由を言語化する)を配置する設計をする
2. 「リードレプリカ」と「キャッシュ」は、どちらも読み取り負荷を減らす手段だが、目的・データの新しさ(整合性)・向いているユースケースがそれぞれ異なる。この差分を、抽象論ではなく今回の具体的なアプリケーション(何をキャッシュするか)に即して説明する
3. キャッシュ戦略を設計する: 何をキー/値としてキャッシュするか、TTL(有効期限)をどう決めるか、DBの値が更新された場合にキャッシュをどう追従させるか(Write-through/Cache-asideなど、方式を選び理由を述べる)
4. キャッシュ自体が落ちた/使えない場合にアプリケーションがどう振る舞うべきか(フェイルオープン: DBに直接見に行く/フェイルクローズ: エラーを返す)を設計判断として決める
5. セキュリティ・可用性・コストの観点も他のお題と同様に整理する

## 前提・制約

- `01-vpc-network`/`03-rds-scaling`/`05-ecs-autoscaling`/`06-multi-az-failure-simulation`で構築したVPC・ECS・RDSの構成をベースにしてよい
- ElastiCacheはノードタイプ次第で時間課金が発生する。設計・レビューが済んだらAWSコンソールでの構築に進み、確認が終わったら速やかに破棄すること
- 今回はアプリケーションコード(実際のキャッシュ読み書きロジック)の実装までは求めない。インフラ設計(ElastiCacheクラスターの配置・セキュリティグループ・パラメータグループ等)と、キャッシュ戦略の設計判断が主目的
