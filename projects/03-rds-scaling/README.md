# 03-rds-scaling

## 課題内容(メンターから提示された要件)

前提として、`01-vpc-network`ですでにRDS Multi-AZ構成を設計・実装済みです(`vpc-network.tf`の`multi_az = true`)。DBの可用性(単一障害点の排除)という設計判断はそこで完了しているものとして、今回はやり直しません。

今回のテーマは、**Multi-AZ構成のままでは解決しない課題**です。

- あなたのWebサービスで読み取りトラフィック(検索・一覧表示など)が増加し、DBへの負荷が高まっているとします
- Multi-AZのスタンバイ側インスタンスは、通常の(Auroraではない)RDSでは読み取りにも書き込みにも使えません(フェイルオーバー専用)。ではこの読み取り負荷の増加に、どう対応しますか?

設計してもらいたいこと:

- 読み取り負荷対策として何を追加するか、なぜそれが適切か
- 追加する構成要素と、既存のMulti-AZ構成(プライマリ/スタンバイ)との役割分担を整理すること(「プライマリ」「スタンバイ」「追加する構成要素」それぞれが何のために存在するか、自分の言葉で説明できるようにしておく)
- アプリケーション側の変更点(書き込みと読み取りで接続先をどう分けるか)も考慮すること

設計がまとまったらAWSコンソールで実際に構築し、以下を実機で観察します(実機確認の価値が高い課題のため、確認後は`destroy`する前提で`apply`してよい。詳細はレビュー時に相談する)。

- Multi-AZの手動フェイルオーバー動作(`01-vpc-network`では設計・実装のみで実機観察はまだのため、今回初めて確認する)
- 追加した構成要素のレプリケーション遅延(プライマリへの書き込みが、どのくらいの時間差で反映されるか)

## 前提・制約

- `01-vpc-network`で構築したネットワーク構成(3層VPC、パブリック/プライベートサブネット)およびRDS Multi-AZ構成を流用してよい。ネットワーク・可用性側の設計をゼロからやり直す必要はない
- チーム体制: 3人程度で運用兼任(`01-vpc-network`と同じ想定)。運用負荷の低さも設計判断の材料にすること
- コスト: 追加する構成要素は追加のインスタンス課金が発生し、通常運用より確実にコストが上がる。設計段階でコスト試算を明示し、実機確認後は速やかに破棄すること

## 設計

### 構成図
- `03-rds-scaling` に記載
- リードレプリカはマルチAZ構成でマルチAZ構成により、可用性を高める

### 使用サービスとその理由

| 用途 | サービス | 選定理由 |
|---|---|---|
|EC2にて、RDSにデータを挿入取得するのに必要なツールをインストールする際の通信に必要|IGW|用途に適合した他サービスはない|
|RDSからのデータ読み取り|EC2|長時間を要さない実験であるため、気軽に起動できるか、必要なツールをインストールしやすいか、RDSと接続できるか、を基準に選定|
|マルチAZ構成やリードレプリカの挙動を確認|RDS|用途を満たすサービスであるため|
|読み取りリクエストの受付|リードレプリカ|プライマリインスタンスの負荷分散をさせるため。キャッシュはそもそも頻繫に更新されるようなデータの保存には適さないので、その場合にはリードレプリカをえらんだほうがいい。なので、要件次第（セッションを保存などはキャッシュサービスでよい）でここは変わる|

### DB関連の役割
- マルチAZ構成
  - プライマリにて読み書きリクエストを処理する
  - スタンバイはプライマリインスタンスがダウンした際に切り替えるために用意されている
- リードレプリカ
  - プライマリインスタンスの負荷を軽減させるために配置する
  - 読み取りリクエストはリードレプリカ、書き込みリクエストはプライマリ
  - アプリケーション側で、エンドポイントを読み取り用と書き込み用で分ける必要がある
- レプリケーション
  - マルチAZ：同期
    - 目的は可能な限りデータの損失を0に近づけることで、同期によって、スタンバイインスタンスにて更新完了した後にレスポンスを返すようにすることで、レイテンシは高くなるがデータの損失を少なくすることが可能
  - リードレプリカ：非同期
    - 目的は負荷分散であるため、多少の不整合は許容し、ユーザへのレスポンスを早めたいという設計思想

### SG設計
- EC2
  - Inbound
    - SSH
  - Outbound
    - DNS
    - HTTP(S)
    - RDSのSG、ポート3306
- RDS
  - Inbound
    - RDSのSG(自己参照)、ポート3306
    - EC2のSG、ポート3306
  - Outbound
    - RDSのSG（レプリケーション通信）、ポート3306

### NACL設計
- EC2配置のサブネット
  - Inbound
    - SSH 0.0.0.0/0 ポート22 Allow
    - TCP 0.0.0.0/0 ポート1024-65535 Allow
      - HTTP(S)：EC2にてMySQLツールをインストールする際の通信
      - MySQL：EC2とRDS通信
    - UDP 0.0.0.0/0 ポート1024-65535 Allow
      - DNS：EC2にてMySQLツールをインストールする際の名前解決
    - その他 Deny
  - Outbound
    - DNS 0.0.0.0/0 ポート53 Allow
    - HTTP(S) 0.0.0.0/0 ポート80, 443 Allow
    - TCP 0.0.0.0/0 ポート1024-65535 Allow
      - SSH：EC2にて作業する際の接続手段
      - MySQL：EC2とRDS通信
    - その他 Deny
- RDS配置のサブネット
  - Inbound  MySQL, レプリケーション応答
    - TCP 0.0.0.0/0 ポート1024-65535 Allow
      - EC2からのリクエスト 3306
      - プライマリからのレプリケーションリクエストのレスポンス
    - その他 Deny
  - Outbound
    - TCP 0.0.0.0/0 ポート1024-65535 Allow
      - EC2からのリクエストに対するレスポンス
      - レプリケーションリクエスト3306
    - その他 Deny

- EC2配置のサブネット
  - 0.0.0.0/0 IGW
  - local (明記する必要はない)
- RDS配置のサブネット
  - local(明記する必要はない)
  - RDS配置のサブネットは二つ存在するがどちらも同じ設定とする

### セキュリティ設計
- 必要最小限を意識し、SG、 NACL、 ルートテーブルの設計を行った

### 可用性設計
- リードレプリカをマルチAZに配置することで可用性を確保
  - コストが高くなるので、コスト重視か可用性重視かで選択は変わる
  - 仮にプライマリとリードレプリカ1台ずつ別のAZに配置しても、片方がダウンすると処理が一つのインスタンスに集中することになる
- マルチAZ構成で可用性を確保
- EC2も可用性を確保すべきだが、長時間稼働のワークロードではない&DBの挙動確認が目的のため、単一AZとした

### コストの見積もり・意識した点
- `db.t3.micro` 4台1時間として約0.21ドル
- `汎用 SSD (gp2)` 毎月 USD 0.138/GB
  - テストで数件程度のデータのみを入れるので0と見なして良い
- `t3.micro` 1台1時間として約 0.01ドル
- 合計約0.44ドル
  - (0.21+0.01) * 2 = 0.44
  - 構築から実験まで2時間想定
- リードレプリカは一つでいいのかどうか、という点を意識して `可用性設計` にその旨の記載をした

## 実装

### AWSコンソールでの構築記録
- 構築し、動作確認にてマルチAZのフェイルオーバーやリードレプリカの挙動を確認し、リソースはすべて削除済み
- つまずいた点
  - DBサブネットグループ名が数字始まり(`03-`)だと作成エラーになった(命名規則の制約)
  - RDS作成時の「EC2インスタンスと接続する」チェックにより、既存のサブネットグループ・SGを使わず、別のサブネット・SGが自動生成された(既存のNACL/SG設計をバイパスしてしまうため、チェックを外して作成し直した)
  - デフォルトでSecrets Managerによるマスター認証情報管理が有効になっており、この状態ではリードレプリカを作成できなかった(統合を解除して手動パスワード管理に変更)
  - ストレージタイプが初期設定で`io2`+プロビジョンドIOPSになっており、想定(`gp2`)よりコストが高い設定だった(作成後に`gp2`へ変更)
  - フロント側(ブラウザ)の入力検証で止まったリクエストはCloudTrailに記録されない(AWSのAPIまで到達していないため)

## わからなかったこと・迷ったこと
- マルチAZ構成、リードレプリカがそれぞれ同期処理が同期的か非同期かの理由がわからなかった
  - マルチAZ構成：目的はデータの損失を限りなく0に近づけることであり、非同期で処理が行われて仮にそれが失敗した状態でプライマリがダウンすると、その書き込み処理による変更が損失することになるので、多少のレイテンシを犠牲にしてでもデータの損失を抑える設計思想になっている
  - リードレプリカ：同期処理が同期だと処理の完了を待ってからレスポンスが返ってくるので非同期に比べてレイテンシが高くなる。リードレプリカの目的は読み取りリクエストを受け取ってパフォーマンスを高めることにあるので、同期処理を同期にすると目的と反してしまうため、非同期で行われる
- リードレプリカとマルチAZ構成でエンドポイントが分かれる理由がわからなかった
  - Auroraは別だが、そもそもリクエストをLBのように分散させる仕組みがないためエンドポイントをわけている
