# 2026-07-14: 03-rds-scaling(出題〜設計レビュー完了)

- 種別: 出題、設計課題(設計レビュー)
- 内容:
  - `docs/ROADMAP.md`のPhase 1未着手項目のうち`03-rds-scaling`を出題した。CURRENT_LEVELで「ほぼ理解できていない」に分類されていたRDS Multi-AZとリードレプリカの目的差分を狙った課題。実機確認(手動フェイルオーバー、レプリケーション遅延の観察)まで行う想定で、MENTOR_RULESの「apply価値が高い課題」の例に合致するため、コンソール構築時のapplyを許容する旨をREADMEに明記した
  - 初版の出題文は「可用性の課題とパフォーマンスの課題を両方提示し、それぞれに適切なRDS機能を選ばせる」という建て付けだったが、ユーザー本人から「RDS Multi-AZは`01-vpc-network`で既に設計・実装済みではないか」と正しい指摘を受け、即座に「Multi-AZだけでは解決しない読み取りスケーリングの課題にリードレプリカで対応する」という差分に絞った出題文に修正した
  - 設計段階で、EC2配置(public/privateとSSHアクセス手段)、SSM Session Managerの要否、Multi-AZ/リードレプリカの理解度の非公式チェックなど、複数の論点を対話しながら詰めた。EC2はpublicサブネット配置・SSHアクセスに決定(SSMは今回見送り)
  - 設計レビューを実施し、初回は「使用サービスの選定理由が文書化されていない」「NACLにエフェメラルポートの考慮が抜けている」等の理由で差し戻し。以後、使用サービスの理由・役割分担の明文化・コストの数値見積もり・NACL設計を複数ラウンドかけて修正し、最終的に合格。`projects/README.md`の状態を「AWS構築中」に更新した
- 発見:
  - 出題の前提確認: 既存実装(`01-vpc-network`のvpc-network.tf、REVIEW.md)を正確に参照した上で出題の誤りを指摘できたのは良い兆候
  - RDS Multi-AZ/リードレプリカの理解度チェック(非公式)で新たな誤解が判明した。(1)「Multi-AZのスタンバイにコールド/ウォームの切り替えがある」という誤り(実際は常時稼働のホットスタンバイ)、(2)「リードレプリカのプロモートはAurora限定」という誤り(標準RDSでも可能)。一方、Multi-AZ/リードレプリカの同期/非同期の理由や、エンドポイントの挙動差については自力で正しく整理できた
  - **NACLのエフェメラルポート考慮を、`02-nacl-experiment`で実機検証まで行って習得した直後にもかかわらず、ゼロからの新規設計(今回)では自発的に適用できなかった。** 指摘を受けて「全て許可でよいか」という誤った簡略化を提案する場面もあったが、具体例を1つ示した上で「わからなくなった」と正直に表明した後、最終的にはEC2配置のサブネットについて完全に正しいNACL設計(新規接続=固定ポート、応答=エフェメラルポート)を自力で仕上げられた。知識の定着と新規適用のギャップが実装(Terraform)だけでなく設計段階でも再現される、という`02-nacl-experiment`の教訓が改めて確認された
  - コスト見積もりについて「難しく感じる」「設計に問題が多く不安」という発言があった。技術的な設計力の問題ではなく、AWS料金ページの参照・計算という未経験の作業に対する不安であることを明確にして進めた。最終的にインスタンス台数(4台)の数え間違いも自力で訂正でき、具体的な数値見積もり(インスタンスタイプ・時間単価・合計額)を完成させられた
  - プライマリ⇄リードレプリカ間のレプリケーション通信がNACL/SGの対象になるかは、メンター側も確信が持てず、設計段階での結論を保留し、AWS構築時の実機確認に委ねる判断をした
- CURRENT_LEVELへの反映: (Terraformレビュー・振り返り時にまとめて反映予定。上記の新規判明事項をメモ: Multi-AZスタンバイのコールド/ウォーム誤解、標準RDSリードレプリカのプロモート可否誤解、NACL設計の新規適用ギャップの再現)
