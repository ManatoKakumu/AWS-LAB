# 2026-07-14: 03-rds-scaling(AWSコンソール構築〜実機確認〜フェーズC完了)

- 種別: 実装課題(AWSコンソール構築)、トラブルシューティング、実機検証
- 内容:
  - NACL設計の詰め直し: EC2配置サブネットのInbound/Outboundで、TCP(HTTP(S)・MySQL応答)とUDP(DNS応答)を分けてまとめる設計に修正。プライマリ⇄リードレプリカ間のレプリケーション通信について、当初「プライマリ用/リードレプリカ用でNACLを分ける」方針を選んだが、`.drawio`を確認した結果、AZ1・AZ2どちらのサブネットにもプライマリ系・リードレプリカ系のインスタンスが1台ずつ同居する構成だったため、役割ベースのNACL分割は物理構成と矛盾すると気づき、両サブネットに同一の統合ルールを適用する方針に修正した
  - SG設計も、NACLと同様にRDS側のOutbound(自己参照、レプリケーション用の新規接続送信)が抜けていたことに気づき追記
  - IAMユーザー(閲覧専用、Describe系のみ)を作成し、メンター(Claude)がAWS CLIで構築内容を確認できるようにした
  - VPC・サブネット・NACL・SG・ルートテーブル・IGWをコンソールで構築し、都度AWS CLIで実際の設定を確認。SG作成時にVPCの選択欄がデフォルトVPCのままになっていた、MySQLルールのポート番号が`0`になっていた、という2つの入力ミスを発見・修正
  - EC2(Amazon Linux 2023)を構築、ユーザーデータで`mariadb105`パッケージをインストールし`mysql`クライアントを導入
  - RDSプライマリ(Multi-AZ)を構築する際、「EC2インスタンスと接続する」チェックにより、既存のサブネットグループ・SGを使わず別のサブネット3つ・SG2つが自動生成される事象が発生。既存の設計をバイパスしてしまうため、生成物をすべて削除しチェックなしで作り直した
  - DBサブネットグループの名前が数字始まり(`03-`)だと作成エラーになることを発見(命名規則の制約)。CloudTrailに記録が出ない理由を、フロント側(ブラウザ)の入力検証で止まったAPIコールは実際にAWSに届いていないため、と正しく推測できた
  - RDS作成時にデフォルトでSecrets Manager連携が有効になっており、この状態ではリードレプリカを作成できないことが判明。統合を解除し手動パスワード管理に変更。またストレージタイプが初期設定で`io2`+プロビジョンドIOPSになっており、想定の`gp2`よりコストが高い設定だったため作成後に修正した
  - リードレプリカを作成し、EC2から`mysql`クライアントでプライマリ・リードレプリカ双方に接続。リードレプリカへの書き込みが拒否されること、プライマリへのINSERTがレプリケーションで反映されること、`ReplicaLag`メトリクスでの遅延測定(ほぼ0)を実機で確認
  - Multi-AZの手動フェイルオーバーをコンソールから実行し、接続の切断・再接続、フェイルオーバー前後でエンドポイントのホスト名は変わらず配置AZのみ入れ替わることを実機で確認
  - すべてのリソース(EC2、RDS×2、DBサブネットグループ、SG、NACL、サブネット、ルートテーブル、IGW、VPC)を削除し、完全に削除されたことをAWS CLIで確認
- 発見:
  - NACLについて、`02-nacl-experiment`で習得した知識(エフェメラルポート考慮)を新規設計に自発的に適用できなかった場面が今回も再度あったが、対話の中で自力で正しい設計に到達できた。一方で「設計図(構成)と実際の物理構成の整合性」という新しい視点への気づきは、こちらが要点を示すまで自力では出てこなかった
  - AWSコンソールの「連携」系の便利機能(EC2インスタンスと接続する、Secrets Manager自動管理)が、意図せず設計をバイパスすることを実体験した。コンソールのデフォルト・自動化機能は便利さと引き換えに設計の制御を失うリスクがあるという教訓
  - CloudTrail(APIコール記録)とクライアント側検証の切り分けを、自分で発見的に推測できた(フロント側で止まったリクエストは記録されない)
  - セッション中盤、学習の焦り・同年代との比較による苦しさを本人から吐露する場面があった。技術力の問題ではなく、前職の学習環境の乏しさによる機会格差であることを確認し、レビュー水準は落とさずセッションのペース配分で調整する方針を確認した。今後NACLの厳密設計は基礎確認止まりとし、ECS Task/Execution Roleなどまだ弱い領域に重点を移す方針も確認した

  - セッション終盤、記録を見ない理解度チェック(10問)を実施。8問は正確(Multi-AZ/リードレプリカの目的差分、書き込み拒否、エンドポイント分離の理由、フェイルオーバー時のエンドポイント不変、NACLの新規接続/応答の区別、SG/NACLの違い、DBサブネットグループの役割、コンソール自動化機能のリスク)
  - 誤解2点: (1)リードレプリカが非同期な理由を「CPU効率」と説明したが、正しくは「同期にするとプライマリの書き込みレスポンスが遅延し、負荷分散という目的と矛盾するため」。(2)Multi-AZフェイルオーバー時のエンドポイント維持の仕組みを「MACアドレステーブル」と推測したが、正しくはDNSレコード(CNAME)の参照先切り替え
  - SGの自己参照ルールがなぜ両方向の通信をカバーするかについて、ステートフル性の説明はできたが、「Inbound自己参照とOutbound自己参照の両方が新規接続それぞれをカバーしている」という構造の説明は半分に留まった
