# 2026-07-25: 06-multi-az-failure-simulation(設計レビュー、フェーズB完了)

- 種別: 設計課題
- 内容: `06-multi-az-failure-simulation`の設計を、構成図・使用サービス・NAT Gateway配置・ルートテーブル・SG・IAM・NACL・実験手順・セキュリティ・可用性・コスト見積もりの順に、セクションごとに提出→レビュー→修正のサイクルで詰めた。今回の核心は「ALBのヘルスチェック失敗時にECSサービスがどう振る舞うか」で、当初ALB・ECSサービス・ECSエージェント・Application Auto Scaling・CloudWatchアラームの役割分担が繰り返し混同された(特に「異常なタスクを止める」の主語をALBだと誤認する誤りが複数回発生)。記録を見ない理解度チェック(8問、1問ずつ)を2巡実施し、最終的にはすべて正確に回答できた。設計面では、NAT Gatewayの配置判断(ポートスコープに基づき単一AZでも実験の妥当性が損なわれないこと)、Application Auto Scalingが今回の検証目的には不要と自ら判断して削除したこと、ALBをinternalスキームに変更する判断などができた。一方で、`05`からの記述の使い回し(コスト見積もりのクロスAZ通信費、Auto Scaling前提の文言)を機械的にコピーしてしまい、アーキテクチャの変更(単一AZ→マルチAZ)に伴う前提の変化を反映し忘れる、という新しいミスパターンが複数回発生した
- 発見: 良かった点は、ECSサービスの役割分担について、単なる「別々の独立した仕組み」という理解から、「2つの独立した入力が同じECSサービスの調整ループに合流する」という統合的な理解まで自力で到達できたこと、SGでは配置AZごとの出し分けができないという制約を自分で気づき、代替手段(NACL)を選べたこと。改善が必要な点は、既存資料を転用する際に「前提条件がアーキテクチャの変更によって崩れていないか」を横断的に見直す視点。これは`01`〜`05`で継続していた「コピペ実装時の値の見直し漏れ」パターンの、Terraformコードだけでなく設計ドキュメント全般への広がりと言える
- CURRENT_LEVELへの反映: なし(フェーズE振り返り時にまとめて反映する)
- 次回への持ち越し: AWSコンソールでの構築(フェーズC)へ進む。構築時`enable_execute_command`を`false`にすることを忘れないよう申し送り済み。詳細は[REVIEW.md](../../projects/06-multi-az-failure-simulation/REVIEW.md)参照
