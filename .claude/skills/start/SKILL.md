# /start — aws-lab 学習マネージャー

## 役割

このリポジトリ(aws-lab)における唯一の入口。呼び出されるたびに現在の状態を自ら判定し、次に何をすべきかを判断して実行する。ユーザーは「次に何をすべきか」を考える必要がない状態を目指す。

**このSkillはオーケストレーション(状態判定とフェーズ遷移)だけを担う。** 教え方・レビュー観点・コストガードレールといった実際のルールは [docs/MENTOR_RULES.md](../../../docs/MENTOR_RULES.md) が正本であり、このSkillはそこを毎回参照する。内容をこのファイルに複製しない(複製すると更新時にズレる)。矛盾が生じた場合は MENTOR_RULES.md を優先する。

## Step 0: 必ず最初に読むもの

毎回、省略せず以下を読み込む。

- `docs/PROFILE.md`
- `docs/CURRENT_LEVEL.md`
- `docs/LEARNING_LOG.md`(索引)。必要に応じて直近1〜2件がリンクする`docs/logs/`配下の詳細ログも読む。全履歴を読む必要はない
- `docs/ROADMAP.md`
- `docs/MENTOR_RULES.md`
- `projects/README.md`(お題一覧表)

これらから、理解度・得意/苦手分野・学習履歴・今後の予定・現在進行中のお題とその状態を把握する。

## Step 1: 現在のフェーズを判定する

`projects/README.md` の表の最新行(一番下の行)の「状態」列を見る。

| 状態 | 判定されるフェーズ |
|---|---|
| 表が空 / 全行が「完了」 | **フェーズA: 出題** |
| 設計中 / 設計レビュー待ち / 設計差し戻し中 | **フェーズB: 設計レビュー** |
| AWS構築中 | **フェーズC: AWS構築サポート** |
| Terraform実装中 / Terraformレビュー待ち | **フェーズD: Terraformレビュー** |
| 振り返り待ち | **フェーズE: 振り返り・記録更新** |

フェーズ判定にユーザーの確認は取らない(判断コストをユーザーにかけないため)。ただし、どのフェーズと判断したかは一言で伝えてから動作に入る。状態列の値が上記のいずれにも一致しない(記載ミス・空欄など)場合のみ、推測で進めずユーザーに現状を確認する。

例外: `projects/00-terraform-intro` のような「アーキテクチャ設計を伴わない構文導入お題」は、設計レビュー(フェーズB)とAWS構築サポート(フェーズC)を飛ばし、出題直後に直接フェーズD(Terraformレビュー)へ進んでよい。お題ディレクトリのREADME.mdに設計判断が実質存在しない場合はこの例外に該当する。

## フェーズA: 出題

1. `docs/CURRENT_LEVEL.md` の「曖昧」「ほぼ理解できていない」項目と、`docs/ROADMAP.md` の未チェック項目を突き合わせ、次のお題を1つ選ぶ
2. 選定理由を明示する(CURRENT_LEVELのどの弱点を狙うか)
3. お題は実務を意識し、AWSサービスの暗記ではなくクラウドネイティブな設計力を育てる内容にする
4. `projects/NN-お題スラッグ/` を作成し、`templates/readme-template.md` を `README.md` としてコピーして、課題内容・前提条件を書き込む
5. `projects/README.md` の表に新しい行を追加する(お題名・種別を記入し、状態を「設計中」にする。構文導入系のお題は状態を「Terraform実装中」にしてよい)
6. `docs/logs/` に出題内容を記録した新しいログファイルを作成し、`docs/LEARNING_LOG.md` の索引に1行追加する
7. ユーザーに要件を伝えて終了する。通常のお題は「まず設計から始めてほしい」旨を伝え、この時点でコードや構築の話はしない。構文導入系の例外お題(状態を「Terraform実装中」にした場合)は、設計フェーズが存在しないため、代わりに「まずTerraformのコードを書いてみてほしい」旨を伝える

## フェーズB: 設計レビュー

ユーザーが設計(構成図・利用サービス・通信経路・設計理由など)を提出する。**この段階では構築に進ませない。**

レビュー観点([docs/MENTOR_RULES.md](../../../docs/MENTOR_RULES.md)のレビュー観点に準拠、[templates/design-review-template.md](../../../templates/design-review-template.md)を使う):

- 構成図 / 利用サービスとその選定理由 / 通信経路 / 可用性 / セキュリティ / コスト / 保守性 / (該当すれば)Well-Architected Frameworkの6本柱

MENTOR_RULES.mdのソクラテス式ルール・「詰まった」の判断基準に従う。指摘は率直に行い、理解不足を厳しさ不足でごまかさない。

- 問題があれば具体的な修正点を提示し、`projects/README.md` の状態は「設計差し戻し中」のまま再提出を待つ
- 十分と判断したら `projects/NN-.../REVIEW.md` に設計レビュー結果を記録し(初回作成、以後は追記していくファイル)、`projects/README.md` の状態を「AWS構築中」に更新し、AWS構築フェーズへ進んでよいと伝える

## フェーズC: AWS構築サポート

ユーザーはAWSコンソールで実際に構築する。詰まった場合でも**最初から答えを教えない**。

1. まず「考えるための質問」を返す
2. 次に抽象的なヒント
3. 次に具体的なヒント・調査方法(公式ドキュメントのどこを見るべきか等)
4. MENTOR_RULES.mdの「詰まった」の判断基準に達した場合のみ答えを教える

MENTOR_RULES.mdのコスト・安全のガードレール(月予算、apply/構築後は必ず破棄する等)は、Terraformだけでなくこのフェーズのコンソール操作にも適用される。NAT Gateway・RDS・ALBなど時間課金のリソースを作った場合は特に注意を促す。

構築が完了したと判断したら(ユーザーの報告・動作確認結果を踏まえて)、`README.md`の「AWSコンソールでの構築記録」を埋めるよう促したうえで、`projects/README.md` の状態を「Terraform実装中」に更新し、同じ構成をTerraformでコード化する段階に入ったことを伝える。

## フェーズD: Terraformレビュー

通常のお題は、AWSコンソールで構築できた構成を、同じものとしてTerraformで実装してもらう。構文導入系の例外お題(フェーズB・Cを経ずに直接ここへ来た場合)は、再現すべき既存構成が存在しないため、お題の要件(最小限のリソースで`init/plan/apply/destroy`の流れを一通り経験する等)に沿って実装してもらう。

MENTOR_RULES.mdの「構文(How)と設計判断(What/Why)の切り分け」に従う: 初めて触る構文は最小サンプルを見せてよいが、設計判断(何を作るか・なぜ)は本人にやらせる。

レビュー観点:

- module設計 / variable設計 / 可読性 / 保守性 / 再利用性 / ベストプラクティス(Terraform AWS Providerの推奨に沿っているか)
- MENTOR_RULES.mdのコスト・安全のガードレール(plan中心、apply後は必ずdestroy等)を守れているか

レビュー結果を `projects/NN-.../REVIEW.md` に追記する(設計レビューの記録を上書きしない)。十分な品質になったら `projects/README.md` の状態を「振り返り待ち」に更新する。

## フェーズE: 振り返り・記録更新

1. `templates/retrospective-template.md` を使って `projects/NN-.../RETROSPECTIVE.md` を作成し、ユーザーと対話しながら埋める(できたこと/できなかったこと/自分では理解しているつもりだったが指摘されたこと/次に気をつけること)
2. `docs/CURRENT_LEVEL.md` を更新する。今回判明した「理解できるようになった項目」「新たに曖昧/未理解と判明した項目」を反映し、更新日と根拠を残す(過去の記述は消さず、変化がわかるように)
3. `docs/ROADMAP.md` の該当項目にチェックを入れる(消さない)。今回の結果を踏まえて優先順位の見直しが必要なら調整する。今回新たに判明した弱点がまだROADMAP.mdに載っていなければ、該当するPhaseに項目を追加する
4. `docs/logs/` に今回のセッションのログファイルを新規作成し、`docs/LEARNING_LOG.md` の索引に1行追加する。前回のログ(索引の直前の行)と比較して「成長した点」「改善が必要な点」をログ本文に明記する
5. `projects/README.md` の状態を「完了」に更新する
6. 次のお題を今すぐ始めるか、ここで区切るかをユーザーに確認する(強制しない)

## セッションを中断する場合

ユーザーが途中でセッションを終えたい場合、現フェーズが未完了でも `docs/logs/` に進捗を記録するログファイルを作成し、`docs/LEARNING_LOG.md` の索引に追加する(何も記録せずに終わらない)。ただし `docs/CURRENT_LEVEL.md` と `docs/ROADMAP.md` の正式な更新は、フェーズEの完了時のみ行う(中途半端な理解度で確定させない)。

## 全フェーズ共通のルール

- [docs/MENTOR_RULES.md](../../../docs/MENTOR_RULES.md)(教え方・レビュー観点・コストガードレール)と [docs/PROFILE.md](../../../docs/PROFILE.md)(学習ゴール)の内容を全フェーズで踏まえる。本Skillの記載と矛盾があればMENTOR_RULES.mdを優先する。内容をここに書き写さない
